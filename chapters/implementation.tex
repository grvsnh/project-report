\section{Prototype Overview}\label{sec:prototype}
VeerDrishti is implemented as an Android application that combines a live camera feed with
on-device computer-vision inference. It uses Android CameraX for capture, Ultralytics YOLO26 Nano
and its variants for inference, Flutter for the interface, and Android Logcat for diagnostics. The
prototype joins these parts so that detections appear directly over the camera view.

The implemented scope is the capture--inference--visualization loop, demonstrating object detection,
segmentation overlays, and human pose visualization. The combat-vision objective guides the
application, but thermal fusion, open-vocabulary recognition, combat-specific fine-tuning, and
persistent mission recording are extensions that the current prototype does not establish.

\label{end:prototype}
\section{Module Implementation}\label{sec:modules}

\subsection{Input Module}
Android CameraX supplies the live camera input, exposed through the Flutter interface so that the
scene and its overlays are observed together. The portrait and landscape screenshots demonstrate
both orientations. Camera access requires the Android camera permission, and denial or interruption
must be handled before the inference pipeline runs.

\subsection{Preprocessing Module}
Preprocessing is handled by the native YOLO inference pipeline: frame rotation, resizing or
letterboxing, RGB conversion, and input-tensor preparation. Rotation keeps the analysed image
consistent with the device orientation, while resizing and letterboxing adapt the frame to the model
input and preserve the information needed to align output coordinates with the preview. The exact
input resolution and normalization settings depend on the deployed model configuration.

\subsection{Orientation and Coordinate Handling}
Camera frames and displayed previews need not share width, height, or orientation, so orientation is
treated as part of the input contract rather than a cosmetic option. A portrait frame may arrive with
rotation metadata while the preview has already applied its own layout transformation; if these are
ignored, a detection can be correct in model coordinates yet appear shifted, mirrored, or rotated.

The sequence reads the camera rotation, prepares the frame for the selected task, and maps the output
coordinates back to the preview dimensions after inference. The same transformation must hold for the
image, the segmentation masks, and the pose keypoints, which is why the portrait and landscape
demonstrations are useful integration evidence even though they are not accuracy tests. A production
evaluation should record rotation metadata, preview dimensions, crop or letterbox policy, and zoom
state for every run, so that an inference fault can be told apart from a coordinate-mapping fault.

\subsection{Inference Module}
YOLO26 Nano and its task variants form the inference component and run on the device, so the
prototype needs no server per frame. The interface exposes Det, Seg, and Pose modes for detection,
segmentation, and pose output. The model export format, class configuration, and execution delegate
are taken from the application configuration when a reproducible deployment is documented.

\subsection{Task Selection and Threshold Handling}
The task selector changes the output produced by the same camera-to-display workflow. Detection
emphasises rectangular localization and class labels, segmentation adds pixel regions, and pose adds
keypoints and skeletal connections. Keeping the modes in one interface allows their presentation cost
and visual interpretation to be compared without changing the surrounding workflow.

The confidence threshold sets the first filtering boundary for displayed predictions, while the IoU
threshold governs overlap handling where the pipeline applies suppression. A lower confidence
threshold exposes more candidates but adds clutter; a stricter one eases interpretation but hides
weak or partially occluded predictions. Thresholds are therefore experiment configuration, not hidden
interface preferences. The demonstrated configuration uses a confidence threshold of 0.25 and an IoU
threshold of 0.70; these explain the visible output but do not define an optimal combat setting.
Future tests should vary one setting at a time on the same scene and model and record the change.

\subsection{Post-Processing Module}
The native inference output passes to the Flutter YOLOView integration, which renders bounding boxes,
class labels, and confidence values on the live feed. Segmentation mode adds coloured region
overlays, and pose mode displays keypoints with connecting lines. Detection coordinates are mapped to
the displayed preview after rotation, letterboxing, scaling, or zoom so that overlays stay aligned.

\subsection{User Interface Module}
Flutter supplies the interface, camera display, mode controls, and visual output. The screenshots show
confidence and intersection-over-union (IoU) threshold controls, zoom information, and runtime
indicators, which let a user inspect a configuration change without leaving the camera view. Object
labels describe model predictions only; a label alone does not establish hostile intent.

\subsection{Development Logging Module}
Android Logcat records runtime and debugging information during development and testing, supporting
diagnosis of camera initialization, inference integration, and application behaviour. This is
development logging, not a persistent detection-event or mission-video archive; the implementation
contains no demonstrated database, encrypted recording service, or post-mission retrieval interface.

\label{end:modules}
\section{Frame Processing Pipeline}\label{sec:pipeline}
The module descriptions define the following processing sequence for the prototype:
\begin{enumerate}
  \item Initialize the selected camera and model task, then present the live preview once camera
    permission is available.
  \item Obtain an analyzable frame from CameraX and account for its orientation.
  \item Resize or letterbox the frame, convert it to RGB, and prepare the input tensor in the
    native inference pipeline.
  \item Run the selected YOLO26 Nano task variant on the device and obtain its output.
  \item Apply the configured filtering settings and map the resulting coordinates to the preview.
  \item Render labels, boxes, masks, or pose keypoints through YOLOView, display runtime
    information, and continue with subsequent frames.
    \label{end:pipeline}
\end{enumerate}

\section{Interface and Detection Controls}\label{sec:controls}
The demonstration screenshots show a confidence threshold of 0.25 and an IoU threshold of 0.70. The
confidence setting fixes the minimum score accepted for display, and the IoU setting controls overlap
filtering where the pipeline uses it. Because either value changes the visible output, evaluation runs
should record both along with the selected task and model, and should state whether all task variants
share one suppression mechanism.

The interface also displays frames per second and processing times, including preprocessing,
inference, and post-processing components. These help inspect responsiveness during a demonstration,
but they are displayed runtime observations rather than repeated timing measurements on a documented
device. Chapter~\ref{ch:result} records the displayed values and separates them from a sustained
performance benchmark.

\section{Integration and Testing}\label{sec:integration}
Integration testing connects camera capture, model execution, and overlay rendering into one
workflow. The exhibits involve scissors, a mouse, furniture, laptops, bottles, and groups of people,
exercising multiple visible objects and all three task modes; the portrait and landscape exhibits
additionally check preview orientation and output alignment.

The integration boundary has five connected checkpoints: the camera initializes and delivers a frame
after permission is granted; the frame reaches the selected task with the expected orientation; the
inference result returns without blocking the interface; the result is mapped into the preview
without visible displacement; and the interface exposes mode, threshold state, and runtime fields
clearly enough to interpret the output. A failure at any checkpoint can make the final screenshot
appear wrong even when other modules work correctly.

The visible prototype supports functional checks at this boundary: live preview, task switching,
overlays, both orientations, and displayed timing. It does not establish permission recovery after
interruption, long-duration thermal stability, memory behaviour, or reliable operation across
different camera sensors; those belong to a later validation plan on documented hardware.

For reproducible testing, record the Android device and version, application build, model file, task
mode, input resolution, thresholds, and execution backend, and separate functional checks from
accuracy and performance evaluation. A correctly rendered box verifies an interface path, whereas
precision, recall, mAP, and sustained frame rate require defined data and measurement procedures. The
resulting checklist is to verify camera permission and initialization, rotation handling in both
orientations, the selected task and thresholds, overlay alignment after resizing, and visibility of
the runtime readings, and to record the device, build, model, and backend.

\subsection{Implementation Risks and Mitigations}
Camera permission can be denied, revoked, or interrupted when the activity changes state; the
application should offer a clear recovery path instead of running inference on an unavailable frame.
Model initialization can likewise fail through a missing file, an incompatible export, or an
unavailable execution delegate, and logging the stage and selected task separates these failures from
ordinary frame-processing errors.

Orientation and preview scaling form a second class of risk. A frame can be valid while its overlay is
visually wrong if rotation metadata, crop, zoom, or letterbox dimensions are not propagated
consistently; the portrait and landscape views provide a regression pair for checking the same object
after an orientation change.

Runtime stability is a third boundary, since one successful frame does not show that the preview stays
responsive over a session. Repeated runs should record frame-processing behaviour, memory pressure,
device temperature, and the acceleration path, and should distinguish model execution, image
conversion, overlay rendering, and logging overhead when performance degrades. Finally, the interface
must stay legible when many objects, masks, or keypoints are visible: labels should not obscure the
scene, controls should be readable in both orientations, and confidence values are model outputs, not
verified accuracy.

\subsection{Runtime State and Error Handling}
An explicit runtime state sequence simplifies maintenance: start uninitialized, confirm camera
permission, initialize the preview, load the selected model, and only then accept frames for
inference. During a task change the interface should retain the last valid preview or show a loading
state. Treating these transitions as states prevents a temporary camera or model condition from being
mistaken for a detection failure.

Permission is the first recoverable boundary: if it is denied the application should explain why the
camera is unavailable and offer a route to grant access, and if the activity pauses or the camera is
interrupted the preview should follow the CameraX lifecycle. Each accepted frame should be checked for
valid dimensions, rotation metadata, and an available image buffer before preprocessing, because a
malformed frame produces misleading downstream symptoms.

Model initialization is a separate state: a model file can be absent, incompatible with the selected
task, or unable to use the requested execution delegate. The interface should report an
initialization error with the model path, task, and delegate, and any fallback to non-accelerated
execution should be recorded because it changes runtime readings. Intermittent frame failures should
be logged and skipped rather than ending the preview, repeated failures should surface as a warning,
and inference exceptions should not leave a stale overlay on a new frame without indication.

User-controlled settings obey the same rule. A threshold change should apply at a defined pipeline
point and be reflected in the visible control, and the scope of a setting should be clear where task
variants use it differently. Capturing the configuration with each output lets a later review
distinguish a changed threshold from a changed model or scene.

\subsection{Configuration Traceability}
Each demonstration should record the application build, Android version, device model, camera
orientation, preview dimensions, selected task, model file or version, confidence and IoU thresholds,
maximum item setting where applicable, and execution backend, together with whether the frame came
from a live camera or a static test image. Without these fields, two screenshots with different labels
or timings cannot be compared.

The orientation record should contain both source rotation and display orientation, since a ``portrait''
label alone cannot express a rotated buffer shown under a different coordinate convention, and the crop
or letterbox policy and any zoom or digital crop should be recorded because they change overlay
geometry. Runtime fields should be copied exactly as displayed, with label and unit retained, and the
time window, averaging rule, and whether capture is excluded should be documented before any formal
performance claim.

The same record supports debugging: an overlay displaced only in landscape can be investigated by
comparing rotation metadata and preview dimensions while the model and thresholds are held constant,
an inference-time increase after a task change can be compared without a different scene, and a
frame-rate change after a build change has a starting point in the build and delegate record.

\subsection{Validation Matrix and Reproducible Procedure}
A later validation pass is best organised as a matrix. The first dimension is task mode (detection,
segmentation, pose), the second is orientation (portrait, landscape), and the third is scene condition
(clear objects, multiple objects, partial occlusion, small or distant objects, camera motion,
illumination variation). Every cell should use the same model and documented device with repeated
samples under one threshold configuration, and empty cells should be reported as untested rather than
inferred from a nearby condition.

The functional part asks whether the preview initializes, the task loads, the output type renders, and
the overlay stays aligned after orientation and preview-size changes. The measurement part asks for
repeated frame-rate and processing-time samples with the time window and device state. The accuracy
part requires labelled reference data and a matching rule before precision, recall, or mAP can be
computed. Keeping the three parts separate prevents a successful overlay from being treated as
evidence for all three.

A reproducible run records the device, build, model, task, and threshold configuration; starts from a
known lifecycle state and confirms camera permission; lets the preview stabilize; captures a fixed
number of samples with the displayed runtime fields preserved; repeats after changing one controlled
variable such as orientation or task mode; and stores the observations with enough context to identify
the image, configuration, and any failure or dropped frame. Negative and recovery cases belong in the
same matrix: denied permission, an unavailable model, an unsupported task, an invalid frame, an
interrupted session, and an overlay mismatch all mark the boundary of reliable operation and should be
recorded rather than omitted.

The current material supports the successful functional path and the first matrix cells, but it does
not provide the device configuration, repeated sample count, annotated ground truth, or recovery logs
needed for the full matrix. Stating that boundary keeps the chapter reproducible and allows measured
results to be added later without rewriting the existing evidence.
